# Checklist: Datastore Connectors

Detailed verification rules for data format claims, completeness, handler names, parameters, and script fields.

## H2. Data Format and Processing Behavior Claims

- When docs describe what input formats a connector supports (e.g., "reads JSON array files and JSONL files"), verify by reading the actual parsing implementation.
- **Line-by-line vs stream parsing**: Check whether the code reads input line-by-line (`BufferedReader.readLine()` + per-line parse) or uses a streaming parser (e.g., Jackson `JsonParser` with token iteration). Line-by-line readers cannot process multi-line formats like pretty-printed JSON arrays. Example: `JsonDataStore` uses `br.readLine()` + `objectMapper.readValue(line, Map.class)`, so it only supports JSONL (one JSON object per line), not JSON arrays (`[{...}, {...}]`).
- **Type expectations in parsing**: Check `readValue()` target types. `readValue(line, Map.class)` expects a JSON object on each line; a JSON array (`[...]`) would throw `JsonParseException`. Docs claiming array support when the parser expects objects are INCORRECT.
- **Silent failure vs hard failure**: Some parsers wrap individual line parsing in try-catch (continuing on error), while others fail on the first bad line. Check error handling to accurately describe behavior in troubleshooting sections.

## H5. "Common Parameter" Scope Verification

- When docs present parameters in a "共通パラメーター" (common parameters) table, verify that **every listed parameter actually exists in all connector classes** covered by that table. Grep each parameter name across all DataStore classes in the plugin.
- Common pattern: a parameter like `include_pattern` or `default_permissions` exists in most but not all connectors (e.g., present in OneDrive/SharePoint but absent from OneNote/Teams). Listing it as "common" is INCORRECT — move it to the per-connector additional parameters sections.
- To verify: for each parameter in the common table, grep `PARAM = "{param_name}"` across all DataStore classes in the plugin. If any class lacks the constant, the parameter is not truly common.

## H6. Parameter "Required" Column Verification

- When a datastore doc has a parameter table with a "必須/Required" column, verify each entry against the actual code behavior:
  1. **Required = Yes**: The code must throw `DataStoreException` or similar if the parameter is blank/missing. Check for `StringUtil.isBlank(param)` followed by `throw new DataStoreException(...)` patterns in the `storeData()` method.
  2. **Required = No**: The parameter has a default value via `paramMap.getAsString(PARAM, defaultValue)` or is conditionally used.
- A common error is marking parameters as "Required" when they are merely *recommended* for useful output (e.g., `base_url` in Git connector — without it URLs are empty, but the connector runs without error). If code does not throw on absence, report as INCORRECT and change to "No" with a note explaining what functionality is lost.
- Also check the reverse: parameters that ARE required in code (throw on blank) but marked "No" in the doc should be reported as INCORRECT.

## H7. Auto-Managed Parameter Behavior

- Some datastore parameters are **automatically updated** by the system after execution (e.g., `prev_commit_id` in Git connector is updated to the latest commit ID after successful crawl via `updateDataConfig()`). If a doc describes such a parameter as requiring manual updates without mentioning auto-update behavior, report as MISSING.
- **Detection method**: Search for `dataConfig` updates in the `storeData()` method — patterns like `DataConfigBhv.update(dataConfig)`, `handlerParameterMap.put()`, or `updateDataConfig()` indicate auto-managed parameters.
- The fix should explain: (1) the parameter is auto-updated after successful execution, (2) users only need to set the initial value (or leave it empty), and (3) subsequent runs will automatically use the updated value.

## H8. Parameter Value Format Verification

- When docs show example values for parameters (especially in `::` code blocks), verify the **format** matches how the code actually processes the value — not just the underlying system's full API format. Trace the parameter from `paramMap.getAsString(PARAM)` to the library/framework method that consumes it.
- **Library method delegation**: If the connector passes a parameter value directly to a library method (e.g., `QueryBuilders.wrapperQuery(value)`, `objectMapper.readValue(value, ...)`, `new URL(value)`), the expected format is determined by **that method's contract**, not by the underlying system's general API. A common error is documenting the full system API format when the code only passes a subset.
  - Example: Elasticsearch connector passes the `query` parameter to `QueryBuilders.wrapperQuery()`, which expects raw query JSON (e.g., `{"term":{"status":"published"}}`). But docs may show the full Elasticsearch search API format with an outer `{"query":...}` wrapper (e.g., `{"query":{"term":{"status":"published"}}}`), which is INCORRECT because `wrapperQuery()` adds the `"query"` layer itself.
- **Builder method scope**: When a parameter value is passed to a specific builder method (e.g., `builder.setQuery()`), only features within that method's scope are effective. Other search/request-level options (sort, aggregations, source filtering) that are siblings of `query` in the full API cannot be embedded in the same parameter value.
  - Example: A doc showing `query={"query":{"match_all":{}},"sort":[...]}` is INCORRECT if the code only calls `builder.setQuery(wrapperQuery(value))` — the `sort` portion is silently ignored because `wrapperQuery()` treats the entire string as a query body.
  - **Detection method**: Trace from `paramMap.getAsString(PARAM)` to the builder/client method call. If the value is passed to a single-purpose method (e.g., `setQuery()`, `setFetchSource()`), any features outside that method's scope documented as usable via the parameter are INCORRECT.
- **Format transformation before delegation**: Some connectors transform parameter values before passing them (e.g., `trim()`, `split(",")`, `Integer.parseInt()`). Verify that documented example values survive these transformations correctly. Example: if code calls `.trim().split(",")`, a value like `"field1, field2"` would produce `["field1", " field2"]` (note the leading space), which may cause subtle issues.

## J. Duplicate or Missing Entries

- Check for duplicate rows in RST `list-table` directives.
- **Duplicate content blocks**: Check for repeated code blocks or configuration sections within the same RST file. A common pattern is a section (e.g., "最小構成") that shows the same file path and content block twice due to copy-paste errors during doc authoring.
- Check for properties defined in source but missing from doc tables.
- **Properties in code examples but not in formal tables**: Also check for properties that appear only in code examples or troubleshooting sections within the doc without a corresponding formal `list-table` entry. These are easy to miss and should be added to the appropriate table.
- **Crawler client `client.` prefix convention**: In Fess's crawl configuration UI "設定パラメーター" field, parameters use a `client.` prefix (e.g., `client.endpoint`, `client.accessKey`). This prefix is stripped when passed to the crawler client's `getInitParameter()`. Docs should use the `client.` prefixed form since that is what users enter in the UI.
- **UI label files as property completeness cross-reference**: `fess_label_*.properties` contains labels for every configurable property exposed in the admin UI (e.g., `labels.entraid_permission_fields`, `labels.entraid_use_ds`). Grep the label file for the feature prefix (e.g., `labels.entraid_`) and compare the set of properties found against the doc's `list-table` entries. Any label present in the properties file but absent from the doc table is a candidate for a MISSING finding. This technique catches properties defined in `FessProp.java` or other secondary sources that are not in the primary authenticator/helper class.

## J1. Empty or Placeholder Sections

- Check for sections that appear complete (have a heading, description text, and code block) but contain **identical content to another section** in the same file. This is a common copy-paste error where a usage example was duplicated but never customized.
- **Detection pattern**: Compare code blocks across "使用例" (usage example) sections. If two sections have different headings but identical `::` code blocks (especially script blocks), the later one is likely a placeholder that was never filled in.
- Also check that the descriptive text before a code block actually matches what the code block demonstrates. A heading like "特定のフォルダのみをクロール" followed by a script with no filtering logic is a placeholder.

## J2. Plugin Handler Name and Parameter Completeness (Datastore / LLM / etc.)

- **Handler name verification**: Each plugin registers handlers in `fess_ds++.xml` (or `fess_llm++.xml`, etc.) as `<component>` entries. The handler name displayed in admin UI is the class's `getSimpleName()` (inherited from `AbstractDataStore.getName()`). Verify every handler name in the doc against the XML registration and class name.
- **Multiple handlers per plugin**: A single plugin may register multiple DataStore implementations (e.g., `fess-ds-elasticsearch` registers both `ElasticsearchDataStore` and `ElasticsearchListDataStore`; `fess-ds-dropbox` registers `DropboxDataStore` and `DropboxPaperDataStore`). Compare all `<component>` entries in the XML against the doc's handler name list to catch missing handlers.
- **Parameter completeness via `*_PARAM` constants**: Grep each DataStore class for `PARAM = "` to enumerate all accepted parameter names. Compare these against the doc's parameter table. Parameters present in code but absent from the doc should be reported as MISSING. Note that some advanced parameters (e.g., `skip_lines`, `ignore_empty_lines` in CSV) are commonly omitted from docs despite being valid.
- **Parameter naming style inconsistency across plugins**: Fess plugins do NOT follow a single naming convention. Example: `fess-ds-csv` uses `file_encoding` (snake_case) while `fess-ds-json` uses `fileEncoding` (camelCase). Always verify the exact string value of the `*_PARAM` constant — do not assume the naming style from one plugin applies to another. If a doc uses the wrong style (e.g., `file_encoding` for JSON), report as INCORRECT.
- **Parameter interaction, precedence, and error behavior**: When a connector accepts mutually exclusive or alternative parameters (e.g., `files` vs `directories`), verify that docs describe: (1) which parameter takes precedence if both are specified (trace the `if/else` or early-return logic in `getFileList()` or equivalent), (2) what error occurs if neither is specified (e.g., `DataStoreException`), and (3) whether the non-preferred parameter is silently ignored or causes a warning. Example: `JsonDataStore` checks `files` first; only if blank, checks `directories`. If both are blank, throws `DataStoreException`. This precedence/error behavior is commonly undocumented.
- **Parameters in usage examples and code blocks**: Parameter verification must not be limited to formal `list-table` entries. Also check parameters that appear in `::` code blocks within usage examples, troubleshooting sections, and permission configuration sections. A common error is documenting a fabricated parameter (e.g., `default_permissions`) in a usage example that does not exist in any `*_PARAM` constant or in the `AbstractDataStore` base class. Grep the parameter name across both the plugin source and `repos/fess/src/main/java/org/codelibs/fess/ds/` to confirm existence. Also verify the reverse: for each authentication or configuration example in the doc, check that **all required parameters for that code path** are present. A common error is omitting a required parameter from an example (e.g., `password` missing from an OAuth password flow example), which causes user failures when copying the example verbatim. Trace the `getConnection()` or equivalent method's validation checks to enumerate required parameters per auth type, then compare against each example block.
- **Authentication method verification**: When docs list supported authentication methods (e.g., "JWT or OAuth 2.0"), verify each claimed method against the actual implementation. Check how the API connection is created (e.g., `BoxDeveloperEditionAPIConnection.getAppEnterpriseConnection()` = JWT only, not OAuth). Docs claiming authentication methods not implemented in code should be reported as INCORRECT. When a connector supports multiple auth methods (e.g., `oauth_token` vs `oauth_password`), verify each auth example **independently** — each must include all parameters required by that specific flow's code path. A common pattern: the code has separate validation branches per `auth_type` (e.g., `switch(authType)` with different required parameter sets). Cross-check each example against its corresponding branch. Example: Salesforce's `oauth_password` requires `password`, `security_token`, `client_id`, `client_secret` while `oauth_token` requires `private_key`, `client_id` — an example missing any of these for its flow should be reported as INCORRECT.
- **OAuth/API scope verification**: For cloud service connectors (G Suite, Microsoft 365, Box, etc.), verify that the OAuth scope documented for admin console/delegation setup **exactly matches** the scope the code actually requests in the JWT/OAuth flow. Grep the client class for `scope`, `withClaim("scope"`, or `SCOPES` to find the actual requested scope. A common error is docs recommending a more restrictive scope (e.g., `drive.readonly`) than what the code requests (e.g., `drive`), which causes authentication failures because the token request includes an unauthorized scope. If the documented scope differs from the code's requested scope, report as INCORRECT.
- **Base class inherited parameters**: In addition to plugin-specific `*_PARAM` constants, check for common parameters inherited from `AbstractDataStore` (e.g., `readInterval` — delay in milliseconds between processing each record). These base class parameters apply to all connectors but are frequently omitted from per-connector documentation. Grep `AbstractDataStore.java` for `paramMap.getAsString(` or `paramMap.containsKey(` to enumerate inherited parameters.
- **Plugin-specific intermediate base classes**: Some plugins define their own abstract base class between `AbstractDataStore` and the leaf DataStore classes (e.g., `AtlassianDataStore` for Jira/Confluence, `Microsoft365DataStore` for Microsoft 365 connectors). These intermediate classes often define shared parameters (`ignore_error`, `include_pattern`, `exclude_pattern`, `number_of_threads`, `url_filter`, etc.) that apply to all connectors in the plugin but are NOT in the leaf classes or in `AbstractDataStore`. Always check the full class hierarchy: `AbstractDataStore` → plugin intermediate base → leaf DataStore. Grep each level for `PARAM = "` or `paramMap.getAsString(` to find parameters at every level.
- **Plugin client/helper class parameters**: Many plugins have a shared client class (e.g., `Microsoft365Client.java`, `BoxClient.java`) that handles authentication and API communication. These classes often define additional parameters (`proxy_host`, `proxy_port`, `proxy_username`, `proxy_password`, `cache_size`, `max_content_length`, etc.) that are common to all connectors in the plugin but are NOT defined in the DataStore classes themselves. Always grep `*Client.java` and other helper classes in the plugin for `PARAM`, `getAsString(`, or constant declarations to find these parameters. Report as MISSING if they are absent from the doc.
- **Unused/dead constants**: Before documenting a parameter found as a constant, verify it is actually consumed by a `getAsString()`, `paramMap.get()`, or similar call. Constants defined but never referenced in any parameter-reading code are dead code and should NOT be added to documentation. Grep for the constant name (not the string value) to check for usage beyond the declaration line.
- **`*ListDataStore` variant check**: Many plugins register a `*ListDataStore` variant alongside the primary handler (e.g., `CsvListDataStore`, `ElasticsearchListDataStore`). These variants typically extend the base DataStore with: multi-threaded processing (`num_of_threads`), automatic file deletion after processing, and timestamp-based file filtering (`timestamp_margin`, default 10000ms). Always check `fess_ds++.xml` for `*ListDataStore` components and verify they are documented.
- **Overview doc vs repository completeness**: When reviewing overview/index documents (e.g., `ds-overview.rst`), list all `repos/fess-ds-*` directories and compare against the connectors documented. Undocumented repositories (excluding `fess-ds-example`) should be reported as MISSING. Note that some functionality may overlap (e.g., `fess-ds-sharepoint` is a legacy connector while `fess-ds-microsoft365` covers SharePoint via Graph API).
- **Overview doc common settings completeness**: When an overview doc lists "共通設定項目" (common settings), verify it covers all fields in `admin/dataconfig/CreateForm.java` and `EditForm.java`. Common missing fields: `description` (説明), `permissions` (権限), `virtualHosts` (仮想ホスト), `sortOrder` (表示順序). These are part of the admin form but frequently omitted from overview documentation.
- **Overview doc generic parameter fabrication**: Overview docs tend to present "common" authentication or performance parameters (e.g., `client.id`, `client.secret`, `batch.size`, `interval`, `thread.size`, `timeout`) that do not exist as shared parameters in `AbstractDataStore`. The only truly common parameter inherited by all connectors is `readInterval`. Auth and performance parameters are connector-specific — verify each claimed "common" parameter against `AbstractDataStore.java` source. If the parameter does not exist there, report as INCORRECT (J4: fabricated feature) and recommend referring readers to individual connector documentation.

## J4. Fabricated Features in Datastore Documentation

- AI-generated or speculative documentation commonly fabricates advanced integration features that do not exist in the plugin. Always verify that described capabilities are backed by actual implementation code. Common fabrication patterns:
  - **Connection pooling**: Fabricated parameters like `datasource.class`, `pool.size`, `pool.max_connections`. Verify the actual connection mechanism — most connectors use simple direct connections (e.g., `DriverManager.getConnection()` for JDBC), not connection pools.
  - **Parameterized queries**: Fabricated named parameter syntax (e.g., `:param_name`, `${variable}`) in SQL or query strings. Verify whether the connector uses `Statement` (no parameter binding) or `PreparedStatement` (supports `?` placeholders). Named parameters like `:last_crawl_date` are not supported by standard JDBC.
  - **Advanced authentication**: Fabricated OAuth flows, token refresh mechanisms, or certificate-based auth. Verify the actual authentication code path in the client/helper class.
  - **Batch processing / parallel execution**: Fabricated parameters like `batch_size`, `thread_count` for connectors that process records sequentially. Check whether the connector (or its `*ListDataStore` variant) actually supports multi-threading.
  - **Data transformation / filtering**: Fabricated built-in transformation parameters (e.g., `transform_*`, `filter_*`) when the connector only passes raw data to the script engine.
- **Detection method**: For each feature or parameter described in the doc, grep the plugin source for the parameter name or feature keyword. If no matching code exists, report as INCORRECT with a note that the feature is fabricated.

## J3. Datastore Script Field Verification

- Each DataStore connector puts data into `resultMap` with connector-specific key prefixes. These prefixes vary by connector type:
  - CSV: `data.*` (header column names or `cell1`, `cell2`, ...) plus `csvfile`, `csvfilename`
  - Database: column label names directly (NO prefix — `ResultSetParamMap` puts values with the raw column label as key, e.g., `title`, `content`, NOT `data.title`)
  - JSON: `data.*` (JSON field names)
  - Box/Dropbox/Google Drive/OneDrive: `file.*`
  - Dropbox Paper: `paper.*`
  - Slack: `message.*`
  - Jira: `issue.*`
  - Confluence: `content.*`
  - Teams: `message.*`
  - Salesforce: `object.*`
  - Elasticsearch: `source.*` (from `_source`), plus `id`, `index`, `score`, `version`, `seqNo`, `primaryTerm`, `clusterAlias`, `hit` (raw SearchHit object). Note: Elasticsearch `script_fields` results are NOT in `_source` and cannot be accessed via `source.*` — they require `hit.getFields()`
  - Git: direct field names (`url`, `path`, `name`, `content`, `contentLength`, `timestamp`, `mimetype`, `author`)
  - OneNote: `notebook.*`
  - SharePoint DocLib: `doclib.*`
  - SharePoint List: `item.*`
  - SharePoint Page: `page.*`
- Verify that script examples in docs use the correct prefix by checking the `storeData()` implementation for the keys put into `resultMap` or `dataMap`.
- **Verify individual field names, not just prefixes**: A correct prefix does not guarantee the field exists. For each field referenced in a script example (e.g., `issue.key`, `content.author`), verify that the specific suffix (`key`, `author`) is actually put into the map by checking all `issueMap.put()`, `contentMap.put()`, etc. calls. A common fabrication pattern is using plausible field names (like `issue.key` for Jira) that do not exist in the `storeData()` implementation. Report as INCORRECT if the field is not found.
- **Check ALL script examples across the entire doc**: Script field verification must cover not just the formal "スクリプト設定" / "Script Configuration" section, but also script blocks in "使用例" (Usage Examples) sections. Usage examples often contain more complex script expressions that reference fields not used in the basic examples, and fabricated fields are more likely to appear there. Compare every field reference in every `::` code block tagged as a script against the `storeData()` keys.
- **Caution**: Do not assume all connectors use a `data.*` prefix. Each connector has its own key structure — always verify against the actual `storeData()` or `ParamMap` constructor implementation.
- **Overview doc script example representativeness**: When an overview or index doc shows a script example, verify that it clearly states which connector type the example applies to. A common error is showing `data.*` prefix fields as if they are universal, when `data.*` only applies to CSV and JSON connectors. If the example does not clarify its scope, report as INCORRECT and recommend adding a note listing the connector-specific prefixes (see the prefix table above).
- Some connectors also expose metadata fields (e.g., `csvfile`/`csvfilename` in CSV) that are useful but easily overlooked in documentation.
- **Prefer computed resultMap fields over manual concatenation**: The `resultMap` is initialized as a copy of `paramMap`, so raw parameter values (e.g., `base_url`) are accessible in scripts. However, if the connector computes a derived field (e.g., `url` = `base_url + path`) and stores it in `resultMap`, script examples should use the computed field (`url=url`) rather than manual concatenation (`url=base_url + path`). While manual concatenation may work, it is misleading — it implies the user must construct the value, when the connector already provides it. If a script example uses manual concatenation for a field that already exists as a computed value in `resultMap`, report as minor INCORRECT and suggest using the computed field for consistency.

## J5. Example Value Internal Consistency

- When a doc contains multiple code blocks showing the same parameter (e.g., `token=...`, `url=...`), verify the example values are consistent across all sections (Parameter Configuration, Usage Examples, Troubleshooting, etc.).
- A common pattern: the initial "パラメーター設定" / "Parameter Configuration" section uses one example value format while "使用例" / "Usage Examples" sections use a different format. For instance, showing `token=xoxp-...` (User OAuth Token) in the initial example but `token=xoxb-...` (Bot Token) in usage examples, while the doc recommends Bot Tokens. This inconsistency confuses users about which format to use.
- **Detection method**: Extract all values for repeated parameter names across all `::` code blocks in the doc. Flag any inconsistencies that could mislead users about the correct format, recommended value, or expected input.
- Report as INCORRECT if the inconsistency contradicts the doc's own recommendation or best-practice guidance elsewhere in the same file.
