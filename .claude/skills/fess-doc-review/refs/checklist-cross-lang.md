# Checklist: Cross-language Consistency

Detailed verification rules for multi-language documentation consistency.

## K. Cross-language Consistency

- The Japanese (`ja/`) version is the source of truth. Always review `ja/` first, then compare other languages against it.
- Property names and default values must be identical across all languages (`de/`, `en/`, `es/`, `fr/`, `ja/`, `ko/`, `zh-cn/`).
- Only descriptions/explanations should differ between languages.
- When a fix is found, check if the same issue exists in other language versions.
- **Fabricated properties in translations**: Non-ja versions (especially de/es/fr/ko/zh-cn) may contain entirely fabricated property names that do not exist in the source code. This is a known risk with AI-generated translations. When reviewing translated docs, verify that every property key appearing in the translated version also appears in the `ja/` version. Any property present only in a translation but absent from `ja/` is suspect and must be verified against source code.
- **Fabricated capabilities in translations**: More severe than fabricated properties — translated versions may invent entire features or capabilities that do not exist in the source code. Example: `ds-json.rst` translations added HTTP URL support, REST API authentication, and API access examples, but the actual `JsonDataStore` only reads local files via `new File(path)` / `new FileInputStream(file)`. Unlike fabricated properties (which are individual incorrect keys), this pattern creates entire sections of plausible-looking but completely false documentation. Always compare the feature scope described in translations against ja/ and verify any capability claims that seem broader than what ja/ describes.
- **zh-cn punctuation inconsistency**: Chinese documentation files may mix half-width (`,`) and full-width (`，`) punctuation inconsistently. When editing zh-cn files, always re-read the exact target lines before applying edits, as string matching can fail due to punctuation mismatch.
- **RST directive consistency**: RST directives (`.. note::`, `.. warning::`, `.. deprecated::`, `.. tip::`, etc.) must match the `ja/` version. Translations may inadvertently change directive types (e.g., `.. note::` → `.. deprecated::`) which alters the rendered appearance and semantic meaning.
- **Missing sections in translations**: Translated versions may have entire sections or subsections missing compared to the `ja/` source. This is distinct from fabricated content — it's content that was never translated. Compare section headings and code block counts between `ja/` and each translation to detect omissions.
- **Truncated translation files**: A specific pattern of missing content where the translated file is cut off mid-way, losing all subsequent sections. Example: `ds-json.rst` translations contained only the first ~110 lines (through the parameter table) while the ja/ version had 340+ lines including script examples, troubleshooting, and advanced usage. This is more systematic than individual missing sections — it suggests the translation was incomplete from the start. Compare total line counts between ja/ and each translation as a quick sanity check; a translation with significantly fewer lines likely has truncation issues.
- **Generalized technical values in translations**: Translated `.. note::`, `.. warning::`, and explanatory text may replace specific technical values with vague descriptions. Example: ja/ says `` ``-Dfess.port=8080`` がハードコードされています`` but a translation says only "the port is hardcoded" without the specific value. This is harder to detect than fabricated properties because the meaning is roughly correct — but users lose the actionable detail. Always compare note/warning blocks line-by-line against ja/ and verify that specific values (property keys, flags, numbers) are preserved.
- **Structural reorganization in translations**: Translated versions may restructure content by splitting or merging sections differently from ja/. Example: ja/ has one `fess_config.properties` subsection but ko/ splits it into two, changing "two places" to "three places". Compare section heading counts and hierarchy between ja/ and each translation, not just property names and values.
- **Corrupted technical values in translations**: Non-ja versions may contain subtly corrupted URLs, URIs, or algorithm identifiers in default values. Unlike fabricated property names, these are harder to spot because they look plausible. Example: `http://www.w3.org/2001/04/xmldsig-more#rsa-sha256` (correct) vs `http://www.w3.org/2000/09/xmldsig#rsa-sha256` (corrupted path and fragment). This pattern tends to affect all translated languages identically, suggesting corruption at translation time. Always verify technical string values in translated docs against the `ja/` version and source code.
